# 插件运行时加载与多租户隔离设计

## 1. 先回答你的判断（结论）
你的理解**大体正确**，但有一个关键细节要修正：

1. 系统启动时确实只做 `local/s3 driver` 注册，不会立刻按用户配置创建存储实例。  
2. 用户实际使用时才会懒加载：读取当前 workspace 激活配置，解析并构建 Store 实例。  
3. 多用户（多工作空间）并发使用不会互相污染，实例缓存按 `setting_id + fingerprint` 隔离。  
4. 需要修正的点：运行时不是“进行注册”，而是“进行解析与构建（Resolve + Build）”；`register` 只在启动期做一次。

---

## 2. 当前代码对应关系

- 启动注册：`internal/plugin/boot/bootstrap.go`
- 实例缓存与懒加载：`internal/plugin/boot/manager.go`
- 运行时解析（workspace -> setting -> store）：`internal/plugin/service/plugin_service.go`
- 存储业务调用入口：`internal/storage/service/storage_service.go`
- 工作空间字段来源：`internal/framework/security` 中 `Principal.WorkspaceID`

---

## 3. 启动阶段做了什么

启动只做两件插件相关动作：

1. 创建 `Registry`
2. 注册内置驱动 `local.NewDriver()`、`s3.NewDriver()`

这一步可以理解为“注册能力模板”，不触发：
- 读取用户存储配置
- 连接 S3/MinIO
- 构建具体 Store 实例

---

## 4. 请求阶段懒加载流程

以文件下载/预览为例：

1. `file service` 调用 `storage service` 门面（如 `PresignDownloadURL` / `Get`）。
2. `storage service` 转调 `plugin runtime`（`pluginsvc.Runtime`）。
3. `runtime` 根据 `context` 中的 `workspace_id` 查询 `storage_settings` 的激活配置。
4. 组装 `ResolvedStorageConfig`：
   - `setting_id`
   - `platform_identifier`
   - `config_data`
   - `fingerprint`
5. `manager.Resolve()`：
   - 命中缓存直接返回 Store
   - 未命中则 `driver.ValidateConfig + driver.Build` 后写入缓存

这就是你说的“使用时才加载”。

---

## 5. 多用户/多工作空间不会冲突的原因

## 5.1 配置查询隔离
运行时查询条件包含：
- `workspace_id = 当前上下文工作空间`
- `enabled = true`
- `deleted = false`

所以每个工作空间只会解析自己的激活配置。

## 5.2 实例缓存隔离
`Manager.cache` 使用 `setting_id` 作为主键，配合 `fingerprint` 判版本。

- 不同工作空间通常对应不同 `setting_id`，天然隔离。  
- 同一 `setting_id` 配置更新后，`fingerprint` 变化会触发重建。  
- 配置改动时还会主动 `Invalidate(settingID)` 做精确失效。

---

## 6. 关键边界与术语统一

为避免沟通歧义，建议统一这组术语：

- `注册（Register）`：启动期把 driver 放进 registry。  
- `解析（Resolve）`：运行时根据 setting 查缓存/找 driver。  
- `构建（Build）`：真正创建可用 Store 实例。  
- `失效（Invalidate）`：配置变化时移除指定实例缓存。

---

## 7. 时序图（简版）

```text
Server Start
  -> plugin/module.Init
    -> boot.NewDefaultManager
      -> registry.Register(local)
      -> registry.Register(s3)

Request(file api)
  -> file/service
    -> storage/service
      -> plugin/service.Runtime
        -> query active storage_settings by workspace_id
        -> manager.Resolve(setting_id, fingerprint)
           -> hit cache ? return
           -> miss: driver.ValidateConfig + driver.Build + cache store
        -> Put/Get/Presign/Delete
```

---

## 8. 风险与后续可增强点

1. 当前 `setting_id` 需要全局唯一（现有实现已按时间戳生成，满足）。  
2. 若后续支持“一个空间多激活策略（按目录/桶路由）”，缓存 key 需要扩展为路由维度。  
3. 目前单例 Runtime + Manager 足够；若未来多集群可再引入跨节点一致性策略（一般不需要共享实例，只共享配置即可）。

---

## 9. 最终答复（可直接复述）
是的，你的理解基本正确：启动只注册 driver 模板，真正按用户当前工作空间配置去懒加载 Store；多用户并发不会冲突。唯一要改的说法是“运行时不是再注册，而是解析并构建实例”。
