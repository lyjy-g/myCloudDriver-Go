# 项目介绍与功能思路（面试话术）

## 1. 项目背景（30 秒）
这是一个 Go 实现的 MyCloudDrive。核心挑战不是“文件表增删改查”，而是“文件元数据与真实对象存储如何解耦并长期演进”。

## 2. 我的目标（30 秒）
我把改造重点放在插件强相关链路：
- 上层文件模块不感知 Local/S3 差异；
- 关键 CRUD 路径可观测、可补偿、可扩展；
- 设计能讲清楚工程取舍，而不是只写功能。

## 3. 架构拆分（1 分钟）
- **storage/plugin**：定义统一 `Store` 能力（Put/Get/Delete/Presign）。
- **storage/service**：按工作空间解析激活存储配置，返回运行时 Store。
- **file/service**：只依赖最小存储网关（StorageGateway），处理文件业务语义。
- **file/api**：负责请求协议与幂等控制，调用 file service。

一句话：`file` 只关心“要不要读/删对象”，`storage` 才关心“到底是 local 还是 s3”。

## 4. 这次做的工程化改造（核心）
### 改造点 A：文件服务对存储依赖改为接口最小集
- 引入 `StorageGateway`（PresignDownloadURL/Get/Delete）。
- 价值：降低对 `StorageService` 具体实现绑定，后续接入 OSS/OBS 只改插件层。

### 改造点 B：硬删除从“删元数据”升级为“双阶段删除”
- 第一步：删除文件元数据（用户视图立即一致）。
- 第二步：删除对象存储实体（逐 key 执行）。
- 输出 `HardDeleteReport`：请求数、元数据删除数、对象成功/失败数、失败 key。

### 改造点 C：清空回收站同样插件化
- 清空不只删表记录，还对对象存储执行删除，并返回结构化报告。

## 5. 工程取舍（面试加分）
- 没做强事务跨 DB+对象存储（成本高、耦合强），改用“元数据优先 + 失败可补偿”。
- 这在大多数云盘业务是更现实的方案：先保证用户体验，再保障数据清理可追踪。

## 6. 你可以这样收尾
这次改造不是炫技，而是把“能跑”升级为“可扩展、可观测、可持续维护”，这才是生产工程价值。
