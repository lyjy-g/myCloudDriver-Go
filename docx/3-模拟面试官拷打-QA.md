# 模拟面试官拷打（Q&A）

## Q1：为什么要做存储插件化？直接 if/else 不行吗？
**答：**
短期 if/else 可以，长期会把 file 模块和具体云厂商 SDK 绑死。插件化后上层只依赖统一能力接口，新增存储后端只在插件层实现，业务层零改动，这是可持续演进的关键。

## Q2：你说的“插件强相关 CRUD”具体是哪些？
**答：**
我优先改了和对象存储直接耦合的链路：
1) 下载 URL（预签名）；2) 预览内容读取；3) 永久删除；4) 清空回收站。  
这四条直接决定了存储抽象是否成立。

## Q3：永久删除为什么要拆成两阶段？
**答：**
因为数据库和对象存储不能天然做分布式事务。两阶段策略是：
- 先删元数据，保证用户看不到；
- 再删对象，失败就记录报告，后续补偿。  
这是成本、复杂度、可用性的平衡点。

## Q4：如果对象删除失败会怎么样？
**答：**
业务侧仍返回结构化报告，包含失败对象 key。这样可以接补偿任务（定时/队列）重试，不会“悄悄失败”。

## Q5：为什么 file service 还要再抽 StorageGateway？
**答：**
这是为了把依赖收敛到最小能力集合，减少模块边界污染。这样 file service 更易测，替身注入更简单，也避免“上层知道太多存储细节”。

## Q6：多工作空间切换下，token 与 workspace 如何处理？
**答：**
token 只承载用户身份，workspace 用请求头/服务端状态。否则每次切换工作空间都要重签 token，体验和一致性都很差。

## Q7：你怎么证明这是工程化而不是重构重命名？
**答：**
我会给三个证据：
- 边界更清晰：file 不关心 local/s3；
- 失败可观测：硬删除报告可追踪；
- 扩展可验证：新增后端只动插件实现。

## Q8：如果让你继续迭代下一步做什么？
**答：**
1) 把失败对象 key 接入异步补偿任务；
2) 引入对象删除重试与熔断；
3) 将当前内存 file 元数据切换到持久化表，并补充端到端压测指标。
